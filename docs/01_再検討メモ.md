# 初期検討資料の再検討メモ（Fable による批判的レビュー）

- 作成日：2026-09-09
- 対象：`docs/source/2026-09-09_初期検討資料.md`
- 目的：初期資料の主張を一つずつ検証し、要件定義（`02_要件定義書.md`）で採用・変更・却下する判断とその理由を残す

## 1. 中核コンセプトの評価

初期資料の中核「浸水する建物ではなく、浸水したら長期停止する建物を抽出する」は正しい。既存のハザードマップ・不動産系リスクサービスは「地点の浸水深」までしか出さず、「その水が建物の何に届くか」を扱っていない。ここが差別化点であり、変更しない。

ただし、初期資料には次の弱点がある。

| # | 弱点 | 対処 |
|---|---|---|
| 1 | 「ハザード × 脆弱性 × 影響度」の乗算と加重合計の両論併記で、決め切っていない | 段階的マトリクス方式に確定する（後述） |
| 2 | 「重要設備の低層配置」など、公開データで取れない項目がスコア項目表に混在し、一次スクリーニングと二次診断の境界が曖昧 | 項目を「Tier 0：オープンデータ」「Tier 1：管理者入力」「Tier 2：現地調査」に分け、Tier ごとに別のスコア版を持つ |
| 3 | 「不明」の扱い方が方針レベルで止まっている | 不明は「悲観的事前値 + 低確信度」で扱い、ランク付けに実際に効くようにする |
| 4 | 20 項目以上の「最初に決めるべき論点」が未決のまま | 要件定義書で暫定決定として全て決め、前提として明記する |
| 5 | 内水を最優先と言いつつ、内水データの入手可能性が未調査 | 調査結果を反映し、PLATEAU の建物付与リスク属性と東京都の浸水予想区域図で二重化する |
| 6 | プラバリア・GI・センサー連携・流出解析が MVP と将来機能に混在 | MVP から切り離し、フェーズ 2 以降の別モジュールとする |
| 7 | 検証データが自由が丘 1 事例に偏っている | 2019 年台風 19 号など複数の公開事例で「被災・非被災」両方の検証集合を作る |
| 8 | 施設名や地下設備位置を扱う際の情報管理が課題表に載っているだけ | 公開データ層と非公開層をアーキテクチャ上で分離することを要件にする |

## 2. 評価ロジックの再設計

### 2-1. 乗算 vs 加重合計の結論

加重合計は「ハザードがゼロでも影響度が大きければ高スコア」という説明不能な結果を生む。乗算はゼロ要素があると全体がゼロになり、データ欠損に弱い。

したがって、次の**2 段階マトリクス方式**を採用する。

1. ハザード等級 H（0〜4）と流入脆弱性等級 V（0〜4）から「設備被災可能性」等級 P（0〜4）をマトリクスで決める。
2. P と事業影響度等級 I（0〜4）から「対応優先度」等級（A〜D）をマトリクスで決める。
3. データ確信度 C（0〜100%）は別軸で表示し、優先度には「確信度が低い建物は一段階上の確認対象にする」という形でのみ影響させる。

理由：

- マトリクスは専門家が一目で妥当性を判断・修正できる（説明責任を満たす）。
- 各等級の根拠（どのデータからどう決めたか）を建物カルテに 1 対 1 で書ける。
- 重みの微調整ではなく、マトリクスのセルを PoC で更新する運用にできる。
- 連続値スコアが欲しい場合は、等級の裏に 0〜100 の補助点を持たせて並べ替え用にだけ使う。

### 2-2. 「ハザード」の中身を「水位」に統一する

初期資料のハザード項目は「区域に入っているか」と「地形」が混ざっている。要件定義では、すべて**建物地盤面に対する想定水位（m）**に変換して等級化する。

- 洪水（想定最大・計画規模）の浸水深
- 内水（都市型豪雨）の浸水深
- 高潮の浸水深（沿岸低地のみ）
- 過去浸水実績の有無（水深不明なら「実績あり」フラグ）
- 地形補正：局所窪地・谷底低地・周囲平均標高との差（水位を 1 段階引き上げる補正としてのみ使う）

### 2-3. 「建物脆弱性」を「流入脆弱性」に絞る

一次スクリーニングでは「水が地下・低層の設備空間に届きやすいか」だけを見る。設備の実際の設置階は Tier 1 で入力させる。

Tier 0 で使う代理指標：

- 地下階数（PLATEAU `storeysBelowGround`）
- 建物規模（延床面積・階数・建築面積）：大規模ほど地下設備空間を持つ確率が高い
- 用途（商業・駅・オフィス・病院・物流・データセンター等）
- 建築年（古いほど設備更新・止水対策が未実施の確率が高い代理指標。弱い指標として扱う）
- 敷地の相対標高（建物周辺の DEM が道路面より低いか）

### 2-4. 「事業影響度」は用途主導とする

Tier 0 では用途 × 規模 × 地域拠点性（駅乗降客数、医療・福祉の有無、代替施設距離）で決める。復旧難易度・全館停止可能性は Tier 1 に送る。

## 3. スコープの決定（初期資料 19 章の論点への回答）

| 論点 | 決定 | 理由 |
|---|---|---|
| 対象ユーザー | 第一段階は自社グループの施設管理部門。設計は外販可能な汎用構造にする | 検証データ（設備位置・被災履歴）を得られる相手から始めないと精度検証ができない |
| 対象地域 | 目黒区・世田谷区を PoC エリア、渋谷区・大田区・川崎市を拡張候補 | 自由が丘の事例、東急線、内水リスク（呑川・目黒川流域）が揃う |
| ハザード優先度 | 内水 > 洪水 > 高潮。津波は対象外 | 都市型豪雨が主題。高潮は大田区・川崎の低地でのみ有効化 |
| 用途優先度 | 商業施設・駅ビル・オフィス。病院・福祉は影響度フラグとして使う | 自社事業と検証事例に直結 |
| 評価単位 | PLATEAU 建物 ID。複数棟施設は「施設」グループを任意で持てる | 建物単位でしかデータが揃わない |
| 周辺流況解析 | MVP 対象外。フェーズ 2 で DEM 流下方向解析を追加 | 一次スクリーニングの精度検証が先 |
| 出力 | 優先度ランク + 要因内訳 + 不足情報 + 対策候補（ルールベース） | 対策提案は差別化点だが、MVP では設計ではなくメニュー提示に留める |
| 非公開情報の管理 | 公開データ層（配布可能）と非公開層（テナント別、権限管理）をデータモデルで分離 | 設備位置はセキュリティ情報 |
| 説明責任 | 全等級に根拠データ・出典・取得日を持たせる | 「スクリーニング」と明示し、安全保証ではないことを免責 |
| センサー・施工提案 | 対策候補メニューに含めるが、効果算定はしない | 効果算定は流出解析が必要 |
| GI 効果算定 | MVP 対象外 | 同上 |

## 4. 名称

仮称は初期資料どおり「浸水時事業停止リスク診断」を採用する。リポジトリ・コード名は `flood-bcp-risk` とする。

## 5. 却下・保留にした初期資料の要素

- スコア配点（40/35/25 点）：加重合計を採用しないため廃止。等級マトリクスに置き換える。
- 「確信度補正」を総合スコアに加算する案：確信度はスコアに混ぜず別軸にする。
- 画像解析による地下入口抽出：フェーズ 3 以降の研究項目として保留。
- リアルタイム連携（降雨予測・センサー・アラート）：フェーズ 3。データ契約（水防災オープンデータは有償）が必要。
